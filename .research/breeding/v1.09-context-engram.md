# v1.09 — Collision-free Context Engram สำหรับ ESP32-S3

## ปัญหาจาก v1.08
v1.08 ใช้ quantized 16-D latent vector เป็น hash key ของ Engram และผล host 100,000 samples ได้ raw 77.5280% แต่ Engram-aided เหลือ 77.1920% จึง FAIL เพราะ noisy latent หลายบริบทตกใน bucket เดียวกันและ memory override raw retrieval ผิด.

## Research insight
Engram ต้นทางเป็น conditional memory: ใช้ deterministic address เพื่อ route memory lookup และเน้น hot path แบบ bounded/zero-allocation. สำหรับ sensor latent บน MCU เราไม่จำเป็นต้องเลียนแบบ token n-gram hash ตรง ๆ; สิ่งสำคัญคือ key ต้อง canonical และเสถียร. รอบนี้จึง breed Engram กับ trajectory context โดยใช้ `(previous_state, dwell_bucket)` เป็น canonical key แทนการ hash latent vector.

## Hypothesis
ถ้า key สร้างจาก trajectory context ที่มีขอบเขตแน่นอน จะกำจัด hash collision ของ v1.08 และใช้ Engram เป็น weak prior เฉพาะเมื่อ confidence >= 3 และ candidate อยู่ห่าง raw nearest ไม่เกิน L1 margin 16.

## Implementation
- 32 previous states × 5 dwell buckets
- candidate 160 B + confidence 160 B = **320 B persistent context memory**
- heap = 0 B, core PSRAM requirement = 0 B
- integer/fixed-point only; ไม่มี float ใน hot path
- lookup O(1) direct indexing; ไม่มี hash/probe/replacement scan
- raw 32×16 INT8 L1 retrieval ยังคงเป็น safety baseline

ไฟล์หลัก:
- `espidf/main/katgpt_context_engram_v109.[ch]`
- `benchmarks/v109_context_engram.py`

## Benchmark protocol
Host deterministic simulator: 100,000 samples/seed × 10 seeds. มี sequential trajectory และ negative-control random transitions. ตัวเลขนี้เป็น host simulation ไม่ใช่ board metrics.

คำสั่ง host:
```bash
python benchmarks/v109_context_engram.py
```

ESP-IDF target commands:
```bash
cd examples/iot/_esp32s3/latent
idf.py set-target esp32s3
idf.py build
idf.py size
idf.py -p COM4 flash monitor
```

## Gates
PASS เมื่อ aided accuracy ไม่ต่ำกว่า raw, random-transition regression <=0.25 pp, memory <= v1.08 Engram table และไม่มี unbounded allocation. BOARD-PASS ต้องมี build/flash/run/serial + memory metrics จาก ESP32-S3 จริง.

## Regression / bottleneck
ข้อแลกเปลี่ยนคือ key นี้เก็บเฉพาะ first-order trajectory + dwell ไม่สามารถแยกบริบทที่มี previous state/dwell เหมือนกันแต่ intent ต่างกัน. ถ้า workload branching สูง memory จะลด confidence และ fallback raw แทน.

## Next hypothesis
ถ้า held-out benchmark ผ่าน ให้เพิ่ม Temporal Derivative Kernel ขนาด 2-bit เป็น context bit เพื่อแยก rising/falling trajectory โดยเพิ่ม memory ให้น้อยที่สุด แล้ววัดว่าช่วย branching workload หรือไม่. ห้ามเพิ่ม feature ถ้า v1.09 ยังไม่ผ่าน negative controls.

## สถานะ
**PROTOTYPE candidate** จนกว่าจะรัน benchmark ที่ commit นี้และมี output ที่ตรวจสอบได้. `BOARD-PASS=NO` ในเอกสารนี้เพราะยังไม่มี serial evidence เฉพาะ v1.09.
